# Performance audit — September 12, 2026

Baseline revision: `7bacb088` (`dev`). The working tree was clean before this
audit. The audit covers the Kotlin/Spring backend, Vue web client, and native
SwiftUI app. Public behavior, ordering, permissions, API contracts, and offline
semantics are regression constraints.

The user stopped the broader audit before its remaining work was complete.
Only the verified units described below were retained. Incomplete changes were
removed from the working tree; the final retained scope is intentionally smaller
than the initial audit scope.

## Measurement approach

- Exercise production code with fixed synthetic fixtures, and compare complete
  results with the original implementation or independently specified expected
  results.
- Use deterministic work counts where possible: actual Hibernate SQL statement
  counts, rows/entities loaded, formatter constructions, collection visits, and
  unreleased object URLs. These measurements do not depend on machine speed.
- Report timed microbenchmarks separately from end-to-end latency. Warm up the
  measured code, use repeated samples, and keep the input and runtime identical.
  A faster isolated operation does not imply the same speedup for a whole page,
  API request, or app launch.
- Keep timing thresholds out of normal correctness tests. Preserve reproducible
  benchmark commands and regression checks for the removed repeated work.
- Verify affected tests before broader platform checks. Do not run native UI
  tests or restart the user's development servers.

## Backend: Todo attachment existence

Commit: `c7357b71`.

List responses previously called an attachment existence query once per Todo.
They now select the distinct matching Todo context IDs in one scalar query,
then look them up in a set. Single-item mutation responses retain their existing
path. An empty list does not query attachments.

The integration test flushes and clears the persistence context and resets
Hibernate statistics before each request. Its fixed fixture includes owned and
shared Todos, all three statuses, multiple attachments, attachments in a
different context, deleted attachments, and unattached upload sessions. It
checks every response DTO as well as the SQL count.

| Request | Returned Todos | SQL before | SQL after |
| --- | ---: | ---: | ---: |
| Board | 90 | 92 | 3 |
| Month | 90 | 92 | 3 |
| Date | 90 | 92 | 3 |
| Todo list | 30 | 32 | 3 |
| Completed list | 30 | 32 | 3 |
| Status list | 30 | 32 | 3 |
| Overdue list | 60 | 62 | 3 |
| Empty board | 0 | Not sampled in RED run | 2 |

For the 90-row requests, this removes 89 statements (96.7%). This is a SQL
round-trip reduction, not a claim of a 96.7% request-latency reduction.

The new test failed on the original code only on its seven nonempty query-count
assertions. The following focused verification then passed 215 tests:

```sh
./gradlew test \
  --tests '*TodoReadQueryIntegrationTest' \
  --tests '*TodoServiceTest' --tests '*TodoRepositoryTest' \
  --tests '*TodoControllerTest' \
  --tests '*AttachmentServiceTest' --tests '*AttachmentRepositoryTest' \
  --console=plain
```

Read the `PERF todo-read` lines in
`build/test-results/test/TEST-com.tistory.shanepark.dutypark.todo.service.TodoReadQueryIntegrationTest.xml`
for reproduced statement counts. The assertion intentionally fails when run
against the original production implementation.

## Web: calendar display and date formatting

Commit: `04a2b722`.

The calendar now groups D-Days by their parsed local date and derives visible
schedule tag members in computed values. The schedule cache uses object identity
because separate occurrences with the same schedule ID can carry different
data. Nested changes, a different viewed member, and input order remain reactive.
Only the three displayed schedules per cell need tag derivation.

Date display functions reuse `Intl.DateTimeFormat` instances for the active
locale and options within one JavaScript work batch. A microtask releases the
cache so subsequent batches observe system timezone changes. Invalid dates
still throw, and date-only/midnight/localized display follows the original code.

| Fixed workload | Work measured | Before | After |
| --- | --- | ---: | ---: |
| 200 schedule date ranges | Intl formatter constructions | 400 | 2 |
| 42 cells, 100 D-Days | D-Day parses on mount | 4,200 | 100 |
| 126 visible schedule occurrences | Tag derivations on mount | 756 | 126 |
| Change highlighted date only | D-Day parses | 4,200 | 0 |
| Change highlighted date only | Tag derivations | 756 | 0 |

The regression tests exercise the actual `DutyCalendarContent` component and
calendar grid through Vue's test host renderer. They cover same-ID occurrences,
nested tag/profile changes, the viewed member, date normalization, D-Day order,
click payloads, locale changes, timezone changes between work batches, and invalid
dates. The opt-in benchmark records output SHA-256 values to compare the complete
displayed text between revisions, and removes spies from its timing intervals.

```sh
cd frontend
node scripts/benchmark-web-performance.mjs --baseline-ref=7bacb088
node scripts/benchmark-web-performance.mjs
```

The baseline command copies the current harness/configuration into a temporary
directory and replaces only the two measured production modules with their
original source. It never overwrites the shared working tree. Each timing run
uses three warm-up iterations and nine retained samples in `Asia/Seoul`.
Calendar timings describe Vue host-renderer CPU work; they do not measure browser
layout, paint, network time, or device FPS.

At this commit, the web type check, production build, and full suite passed
(888 tests; two opt-in benchmarks skipped), followed by the final focused checks.
Manual verification used the designated local account and existing development
servers: desktop and 390px mobile viewport, light/dark themes, Korean/English,
next/previous month, opening an existing day's schedule and its localized date,
and Escape dismissal. Console errors were absent. Language, theme, and viewport
overrides were restored after the checks.

## Backend: JWT authentication

Commit: `a819a2af`.

The filter now obtains an authenticated request-local member from a single token
parse. The configured JJWT parser is reused; token claims, member DTOs, session
checks, and authorization decisions are not cached between requests.

The measurement runs the real filter, authentication service, JWT provider, and
JJWT signature parser with mocked database boundaries. The same deterministic
HS256 token is submitted twenty times. A spy counts actual signed-claims parses;
the parser builder returns that real parser so construction requests can also be
counted without replacing signature verification.

| Work for 20 bearer requests | Before | After |
| --- | ---: | ---: |
| Signed-claims parses | 60 | 20 |
| Parser builds during requests | 60 | 0 |
| Parser builds at provider initialization | 0 | 1 |
| Session validity checks | 20 | 20 |
| Member repository loads | 20 | 20 |

Both runs recorded input SHA-256
`83a35f75e36390a0d8661561efec1eef8a233866d35bb0ba68eefc70049cce9b`.
The new code also passes the twenty-request cookie variant. The original cookie
variant was skipped by fail-fast after the intended bearer count failure, so
the before/after table describes the measured bearer path only.

Regression checks cover credential priority and fallback, malformed/expired/
unsupported/wrong-signature/invalid-claims tokens, cookie clearing, revoked or
suspended sessions, impersonation ownership, legacy sessionless tokens,
revocation on the next request, and expiration across a controlled clock boundary.
Each request receives a distinct member DTO. The focused run passed 85 tests:

```sh
./gradlew test --tests '*JwtAuthenticationTest' --tests '*JwtProviderTest' \
  --tests '*AuthServiceTest' --tests '*JwtAuthFilterTest' --console=plain
```

The `JWT_AUTH_WORK` lines in the test XML report reproduce the work counts.
These counts describe cryptographic/parser work, not HTTP latency or throughput.

## Web: profile image lifecycle and duplicate rendering

Commit: `260b28e7`.

Profile image requests now discard and release object URLs from outdated or
unmounted requests. The uploader releases its displayed, replaced, and uploaded
preview URLs on teardown. This prevents a request finishing after unmount from
leaving a blob URL alive, and prevents an older response replacing the current
image.

The member page now mounts one responsive uploader instead of two uploaders
hidden at different CSS breakpoints. The original small/large sizes and crop
interaction remain the same.

| Fixed member-page interaction | Before | After |
| --- | ---: | ---: |
| Uploader instances | 2 | 1 |
| Crop-modal instances | 2 | 1 |
| Initial profile-image fetches | 2 | 1 |
| Fetches through one upload and version refresh | 4 | 2 |
| Live URL after a late response to an unmounted uploader | 1 | 0 |

The tests mount the actual member view/uploader, track live URLs, and cover
out-of-order fetches, version changes, upload/unmount races, replacement,
teardown, and the upload callback. Focused verification passed 26 tests before
the final retained-tree run.

Manual verification checked the desktop profile/crop modal and the 390px mobile
layout (80px photo container), one open crop dialog, and close/cancel. No profile
photo was uploaded or deleted manually. Midway through verification, another
project bound `127.0.0.1:5173`, shadowing the existing Dutypark wildcard listener.
The same original Dutypark process was reached through this computer's LAN
address for the remaining checks. Neither development server was stopped or
restarted. Temporary viewport overrides were reset.

## iOS: paginated list merging

Commit: `a0f953e2`.

Notifications, inquiries, and reports now construct a set of existing IDs once
per incoming page instead of searching the existing array for every incoming
item. Existing rows win over duplicate incoming IDs; the page's order and its
own internal duplicates remain unchanged. No pagination or feedback behavior
changes.

The retained benchmark compiles the actual before/after merge blocks and
unchanged production DTOs with `swiftc -O`. It uses Combine `@Published` arrays,
alternates the two implementations across seven rounds, and compares full
outputs for empty, disjoint, overlapping, and internally duplicated pages before
timing. Inputs include 0, 20, 200, and 2,000 existing rows.

After stopping all subagents, the benchmark was rerun on the exact retained
implementation. Median time for 500 merges with 2,000 existing rows:

| List | Incoming rows | Before | After | Speedup |
| --- | ---: | ---: | ---: | ---: |
| Notifications | 20 | 325.22 ms | 54.47 ms | 5.97× |
| Inquiries | 10 | 174.36 ms | 54.80 ms | 3.18× |
| Reports | 10 | 128.51 ms | 47.73 ms | 2.69× |

All 48 equality cases passed. Empty and small inputs also improved in this run.
These are macOS merge CPU measurements, not iPhone rendering or network timings.

```sh
python3 ios/scripts/benchmark-pagination-merge.py --baseline 7bacb088 \
  --output /tmp/dutypark-retained-pagination
```

The output directory includes the original/current source, their hashes, Swift
version, generated harness, raw samples, and medians. Three app-level regression
tests exercise `NotificationStore` and `SupportViewModel`, including pagination
state and incoming duplicate ordering.
